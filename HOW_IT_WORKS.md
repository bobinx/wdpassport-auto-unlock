# How Western Digital Drive Encryption and Auto-Unlock Work

This document explains the hardware encryption architecture of Western Digital My Passport drives, the SCSI protocol used to unlock them, and the technical implementation of `wd-auto-unlock`.

---

## 1. Hardware Architecture of WD My Passport Drives

Western Digital My Passport portable drives are hardware-based **Self-Encrypting Drives (SED)**. Unlike software full-disk encryption (like Linux LUKS or Windows BitLocker) where the host CPU performs AES computations, My Passport drives perform all cryptographic operations in hardware on the drive itself.

```
                      +--------------------------------------------------------+
                      | Western Digital My Passport                            |
                      |                                                        |
[ Host Computer ]     |  +--------------------+       +---------------------+  |
(Linux /dev/sdX) <==> |  | USB-SATA Bridge    | <===> | SATA Hard Drive     |  |
  SCSI / SG_IO        |  | Controller &       |       | (Stores Ciphertext) |  |
                      |  | Hardware AES Engine|       +---------------------+  |
                      |  +--------------------+                                |
                      |       |           |                                    |
                      |       v           v                                    |
                      |  [ LUN 1: VCD ]  [ NVRAM / Reserved Sectors ]          |
                      |  (SmartWare ISO) (HSB1: Salt, Iterations, Encrypted DEK)|
                      +--------------------------------------------------------+
```

### The USB-SATA Bridge Chip
Inside the enclosure, the SATA drive connects to a custom USB-to-SATA bridge controller (such as chips from Initio, Symwave, JMicron, or Western Digital's proprietary ASICs). This bridge chip contains:
1. **USB 3.0 / USB-C Mass Storage Controller** implementing the USB Mass Storage (BOT) or USB Attached SCSI (UAS) protocol.
2. **Hardware AES Cryptographic Engine** operating in real-time at full SATA line rate (AES-128 or AES-256 in CBC or XTS mode).
3. **Firmware & NVRAM** holding drive security state, salt parameters, and the encrypted data encryption key.

### Key Hierarchy: DEK vs. KEK
The security architecture uses two tiers of keys:

1. **Data Encryption Key (DEK)**:
   - A random 256-bit symmetric key generated by the drive's internal hardware random number generator when security is first initialized.
   - The DEK directly encrypts every 512-byte or 4096-byte sector written to the magnetic platters or flash NAND.
   - The DEK never leaves the drive hardware.

2. **Key Encryption Key (KEK)**:
   - Derived on the host from the user's password using an iterative cryptographic key derivation function (KDF).
   - When you set or change a password, the drive encrypts the DEK using the KEK and writes the resulting encrypted payload into a reserved area called the **Handy Store Block (HSB1)**.
   - When you unlock the drive, your password derives the KEK, which is sent to the drive to decrypt the DEK into the bridge chip's AES hardware register.
   - If the user changes their password, only the KEK and the small encrypted DEK block are rewritten; the drive data does not need to be re-encrypted.

### The Virtual CD-ROM (VCD) & Locked State
When an encrypted My Passport drive is connected to power, it boots into a locked state:
- The disk LUN (LUN 0, the real storage capacity) rejects standard read/write requests with SCSI sense code `02/04/01` (*Logical Unit Not Ready, in Process of Becoming Ready*) or `05/20/00` (*Invalid Command Operation Code*).
- Many models expose a second emulated CD-ROM device (LUN 1, Virtual CD / VCD) containing Western Digital's proprietary "WD SmartWare" software installer for Windows and macOS.
- On Linux, this leaves users stuck: Linux sees either an unreadable disk or an emulated read-only CD-ROM, unable to access the real filesystem.

## 2. SCSI Passthrough Protocol

To unlock the drive without Western Digital's proprietary Windows application, `wd-auto-unlock` communicates directly with the bridge controller using vendor-specific SCSI commands over Linux's SCSI Generic (`SG_IO`) ioctl interface.

### Step 1: Querying Security Status (`0xC0 0x45`)
The tool sends a 12-byte SCSI Command Descriptor Block (CDB):

```text
CDB: C0 45 00 00 00 00 00 00 24 00 00 00
```
- Opcode `0xC0`: Western Digital vendor-specific query.
- Sub-opcode `0x45`: Security status request.
- Allocation length: `0x24` (36 bytes).

The drive returns a 36-byte status descriptor:
- **Bytes 0–3**: Magic ASCII identifier `WD` (`0x57 0x44 0x00 0x01`).
- **Byte 24**: Security State Bitfield:
  - `0x00`: Drive has no password set (unencrypted / disabled).
  - `0x01`: Drive is locked (access restricted, requires password).
  - `0x02`: Drive is unlocked (DEK loaded, ready for I/O).
- **Byte 25**: Cipher identifier:
  - `0x00`: None
  - `0x01`: AES-128
  - `0x02`: AES-256 (CBC or XTS)
- **Byte 28**: Key length in bytes (typically 32 bytes for AES-256).

### Step 2: Reading the Handy Store Block (`0xD8`)
If the drive is locked (`0x01`), we must retrieve the salt and KDF iteration count. The tool requests Handy Store Block 1:

```text
CDB: D8 00 00 00 00 00 00 01 02 00 00 00
```
- Opcode `0xD8`: Read vendor non-volatile storage block.
- Block ID `0x00 0x01`: Handy Store Block 1 (HSB1).
- Allocation length: `0x02 0x00` (512 bytes).

#### HSB1 Layout
The 512-byte HSB1 structure contains:
- **Bytes 0–3**: Header signature (`0x00 0x01 0x00 0x00`).
- **Bytes 4–7**: KDF iteration count as big-endian 32-bit integer (typically `1000`).
- **Bytes 8–23**: Salt string (16 bytes, stored in 2-byte spaced format).
- **Bytes 24–509**: Encrypted key blobs and drive metadata.
- **Bytes 510–511**: 16-bit block checksum.

#### HSB1 Checksum Verification
Before using the salt, the tool verifies block integrity using Western Digital's specific checksum formula:

$$\text{checksum} = \left(-\left(\sum_{i=0}^{509} \text{block}[i] + \text{block}[0]\right)\right) \pmod{256}$$

If the computed value matches `block[510]`, the HSB1 block is valid.

### Step 3: Deriving the Password Key (KDF)
Western Digital implements a custom KDF based on iterated SHA-256:

1. **UTF-16LE Password Encoding**:
   The drive firmware encodes user passwords as UTF-16LE without a Byte Order Mark (BOM). An ASCII character `c` becomes two bytes `c \x00`.
   
2. **Salt Formatting**:
   The 16-byte salt from HSB1 is already formatted with alternating zero bytes (`S \x00 A \x00 L \x00 T \x00 ...`). The derivation takes the first 8 even-indexed bytes (`salt[0], salt[2], salt[4], ...`).

3. **Constructing the 32-Byte Password Block**:
   ```python
   # Combine password and salt into a fixed 32-byte block
   pw_block = bytearray(32)
   # First 16 bytes: even bytes from salt
   for i in range(8):
       pw_block[i * 2] = salt[i * 2]
   # Remaining bytes populated from UTF-16LE password bytes
   ```

4. **Iterative SHA-256 Hashing**:
   Starting with the initial digest of the password block:
   ```python
   digest = hashlib.sha256(pw_block).digest()
   for _ in range(iterations):
       digest = hashlib.sha256(digest + pw_block).digest()
   ```
   The final 32-byte digest is the derived Key Encryption Key (KEK).

### Step 4: Sending the Unlock Command (`0xC1 0xE1`)
The tool builds a 512-byte unlock payload:
- **Bytes 0–7**: Unlock header magic signature (`WD` command header).
- **Bytes 8–39**: The 32-byte derived KEK.
- **Bytes 40–511**: Zero padding.

It issues the SCSI unlock CDB:
```text
CDB: C1 E1 00 00 00 00 00 00 02 00 00 00
```
- Opcode `0xC1 0xE1`: Send security credentials / unlock payload.
- Allocation length: 512 bytes (transfer direction: host to device).

If the password is correct:
- The bridge chip clears the locked status bit.
- The DEK is loaded into the AES hardware engine.
- Subsequent `0xC0 0x45` queries return status `0x02` (unlocked).

## 3. Kernel Rescan & Mounting Flow

Unlocking the bridge chip makes sectors readable, but the Linux kernel's block layer still holds the cached state from when the drive was locked (at which point no valid partition table could be read).

To make partitions visible to the operating system without physically re-plugging the USB cable, `wd-auto-unlock` triggers a kernel rescan sequence:

```
[ wd-auto-unlock ]
       |
       | 1. SG_IO ioctl: Unlock drive via 0xC1 0xE1
       v
[ WD Bridge Chip ] -> Hardware unlocks; sectors now readable
       |
       | 2. Echo 1 > /sys/block/sdX/device/rescan
       | 3. blockdev --rereadpt /dev/sdX
       v
[ Linux Kernel ]   -> Reads MBR / GPT partition table from drive
       |
       | 4. Kernel emits KOBJECT uevent: add partition /dev/sdX1
       v
[ systemd-udevd ]  -> Reads filesystem superblock, creates symlinks:
       |              /dev/disk/by-uuid/<UUID> -> /dev/sdX1
       v
[ wd-auto-unlock ] -> Detects /dev/disk/by-uuid/<UUID>
       |
       | 5. mount /dev/sdX1 /media/WD
       v
[ Filesystem Mounted & Ready ]
```

## 4. Distribution Analysis: Python Script vs. Standalone Binary

A common question is whether `wd-auto-unlock` should be distributed as a Python package, a standalone compiled binary, or a single-file script. Below is an engineering evaluation of the options.

### Option Comparison Matrix

| Distribution Format | Target Audience | Installation Effort | Dependencies | Multi-Architecture Support | Binary / Package Size |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Current: Single-File Python Script** | Linux sysadmins, NAS, Raspberry Pi | `git clone` or single `curl` | Python 3.8+ (Standard Library only) | Universal (any architecture running Python) | **~35 KB** |
| **PyInstaller / Nuitka Standalone ELF Binary** | End users who do not want to install Python or clone a repo | Download 1 binary from GitHub Releases | Zero (bundled libc/Python runtime) | Requires separate builds for x86_64, aarch64, armhf in CI | **~12–15 MB** |
| **Python Zipapp (`.pyz`)** | Systems with Python where single-file distribution is preferred | Download 1 executable file | Python 3.8+ | Universal | **~25 KB** |
| **Debian Package (`.deb`)** | Ubuntu, Debian, Raspberry Pi OS | `sudo apt install ./wd-auto-unlock.deb` | `python3` (from apt) | `all` (architecture-independent architecture) | **~40 KB** |
| **PyPI Package (`pip` / `pipx`)** | Python developers, automation pipelines | `pipx install wd-auto-unlock` | Python 3.8+ | Universal | **~35 KB** |

### Evaluation

#### 1. Does it need to be a Python library?
No. While `wd_auto_unlock.py` is written as a clean Python module that can be imported (`from wd_auto_unlock import unlock_drive`), its primary purpose is a **system utility and daemon**. Most users want a CLI command and a systemd unit, not a library they write Python code against.

#### 2. Can we package it as a standalone binary?
**Yes.** Because the tool has zero third-party pip dependencies, it is straightforward to package into a standalone binary:
- **GitHub Releases PyInstaller Build**: A simple GitHub Actions workflow can compile `wd_auto_unlock.py` into a single, self-contained Linux executable (`wd-auto-unlock`) for:
  - `x86_64` (standard PCs, servers, Intel/AMD NAS)
  - `aarch64` (Raspberry Pi 4/5, modern ARM servers)
- Users can download the binary with one `curl` command and run it immediately:
  ```bash
  sudo curl -L https://github.com/bobinx/wdpassport-auto-unlock/releases/latest/download/wd-auto-unlock-linux-x86_64 \
    -o /usr/local/bin/wd-auto-unlock && sudo chmod +x /usr/local/bin/wd-auto-unlock
  ```

#### 3. Why the zero-dependency Python script remains the ideal foundation:
1. **Pervasiveness of Python on Linux**: Every major Linux distribution (Debian, Ubuntu, Fedora, CentOS/RHEL, Arch, Raspberry Pi OS, OpenWrt, Alpine) comes with Python 3 pre-installed.
2. **Zero Third-Party Dependencies**: Because `wd-auto-unlock` uses only Python's standard library (`ctypes`, `fcntl`, `hashlib`, `struct`, `os`, `sys`), there is no need for `pip`, virtual environments, or compilation toolchains.
3. **Auditability**: Hardware disk encryption and disk unlock utilities handle sensitive disk keys and root permissions. A single, readable Python script allows security-conscious users to inspect the code and verify that passwords and keys are not being leaked or mishandled.
4. **Architecture Agnostic**: A 35 KB script runs identically on an x86_64 server, a 32-bit Raspberry Pi 2, or an ARM64 home server without separate cross-compilation builds.

### Recommended Packaging Strategy
To give users the best of both worlds:
1. **Source / Direct Script**: Keep `wd_auto_unlock.py` as a single, zero-dependency script installable via `sudo make install`.
2. **One-Line Install Script**: Provide a curl installer that downloads the standalone executable directly into `/usr/local/bin/wd-auto-unlock`.
3. **Debian Package (`.deb`)**: Build a lightweight architecture-independent `.deb` package in GitHub Actions that places the binary in `/usr/local/bin`, installs `wd-unlock.service` and `wd-unlock.timer`, and configures the udev rule automatically.
4. **Standalone Binary Release**: Build PyInstaller binaries in CI releases for environments where Python is either missing or heavily stripped (such as minimal container appliances).
